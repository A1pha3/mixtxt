## 第一性原理：三个不变量 → 两类场景（详见 01 第〇节）

选型不靠记方案列表，靠**三条不变量**推导：① 静/动之刃（内容能否在请求时按权限门控）② 真理源（Git 文件 / 数据库）③ 作者界面（文件 / 网页）。由此导出两类场景与一条中间态：

| 场景 | 核心特征 | 推荐路线 |
|------|----------|----------|
| **场景 A：AI 改编小说网** | 单作者、Markdown 正本、无数据库、读者只读、Git 版本管理 | 静态站：Astro + Pages CMS（首选）/ Hugo（最快上线）/ Zola（Rust 平替） |
| **场景 B：小说付费平台** | 多本书、付费/VIP、用户、订单、管理后台、AI 生成 | 动态站：Payload CMS 3（首选）/ PocketBase / Next.js / 微信小程序 |
| **中间态：混合付费** | 只有少数章节收费，其余免费 | 静态站 + 付费墙（详见 01 §1.2）；完整付费业务仍走动态 |

**关键判断：付费内容的鉴权必须在服务端（请求时判断），静态站构建后无法做到**——因此完整付费/VIP/订单业务必须用动态方案（付费墙可被绕过）；但**仅少数章节收费可先用混合付费墙**（Memberful / Cloudflare Access / 极小鉴权函数，见 01 §1.2）。

## 全局设计约定（所有方案统一适用）

### VIP 状态 vs 后台角色

- **VIP 是订阅状态，不是角色**。通过 `vip_subscriptions` 表推导，不存储在 `role` 字段
- `role` 仅用于后台权限控制：`user` / `editor` / `admin`
- 管理员（admin）可以同时拥有 VIP 订阅，两个维度互不干扰

### 章节权限判断顺序（固定）

```text
免费章节 -> 可看；未登录 -> 不可看；购买过该章节 -> 可看；购买过整本 -> 可看；有效 VIP -> 可看；否则显示付费墙
```

### 支付安全

- 权限开通只认服务端支付回调，不认前端状态
- 所有支付回调必须幂等（CAS 模式：只更新 `status = 'pending'` 的记录）
- 余额操作使用原子数据库函数，不在应用层分步扣款 + 写单
- 付费正文只在服务端读取后渲染，永远不 props 进 Client Component

### 数据模型核心表

| 概念 | 说明 |
|------|------|
| users | 用户、VIP 状态、角色 |
| books | 书籍元数据、定价 |
| chapters | 章节元数据与正文 |
| purchases | 所有付费行为主记录 |
| vip_subscriptions | VIP 订阅记录 |
| reading_progress | 阅读进度 |
| comments | 评论（可后置） |

### 内容正本策略（选定一种后保持一致，不要混用）

- **Next.js 方案**：本地 Markdown 文件为正本，数据库存元数据索引
- **Payload CMS 方案**：CMS/数据库为正本，Markdown 仅作导出格式

### 场景 A（静态站）共享铁律（详见 03 第一部分）

- 内容正本是 Git 仓库里的 Markdown/JSON 文件，无数据库
- 草稿不进构建、不进搜索、不进 sitemap
- 章节导航不跨书，按 order/chapterNo（Zola 用 weight）排序
- 版权边界：公版或授权才可公开；unknown 不允许公开构建
- 付费边界：完整付费业务切动态方案（文档 02）；仅少数章节收费可混合付费墙（01 §1.2）
