## 〇、第一性原理：三个不变量（先读这一节）

选型不需要死记方案列表。本目录里所有方案，都能从**三条不变量**推导出来——不变量是"根因"，方案只是"结果"。抓住这三条，你带着任何约束都能自己反推出该选哪条路线。

### 不变量 1 — 静/动之刃：内容能否在"请求时"按权限门控
- **能**（服务端在"谁在请求"时决定返回什么）→ 动态方案。
- **不能**（内容在构建时已编译成固定 HTML，所有人看到同一份）→ 静态方案。
- 这是判断"能不能做付费"的唯一根。付费 / VIP / 订单的本质就是"按人给不同内容"，所以**只要出现付费，就必然落在动态一侧**。

### 不变量 2 — 真理源：内容正本是文件还是数据库
- **文件（Git）**：内容即代码。天然版本化（commit / tag / diff）、可审阅、可被 AI 直接读写与 diff。**最利于 AI 自动化与可审计**。
- **数据库（DB）**：内容即数据。服务端按查询返回、结构强约束、支持多作者并发。
- 这条决定"版本管理怎么做"与"AI 怎么接"。

**为什么"Markdown + Git 正本"天然利于 AI（哲学纵深）：**
- 每次改动都是一个 commit——AI 改了什么，在 `git diff` 里**一目了然**。AI 编造情节 / 漏掉伏笔，人能从 diff 直接抓出来，回滚就一条 `git revert`。
- AI 的输入输出都是文本：文件正本让 AI 能**直接读写、逐章 diff、批量重排**；数据库正本的 AI 只能走 API，看不见"改了什么"。
- 这正是"AI 生成草稿、人决定发布"铁律能在 Git 上真正成立的原因：**AI 的每一次产出都可审查、可回滚**。真理解这条，就理解了为什么静态方案天然比动态方案更 AI 友好（代价是放弃付费能力）。

### 不变量 3 — 作者界面：用文件写还是用网页写
- **文件**：作者用编辑器 / GitHub 网页端直接改 Markdown。零后台成本。
- **网页**：作者用站内 CMS 后台（编辑 UI、结构校验、富文本）。要额外引入 CMS 层。
- 这条决定"要不要上 CMS / 编辑界面"，以及"无数据库静态站能否有网页编辑入口"。

> **用三条不变量推导路线：**
> - 要付费（全面收费 / VIP / 订单） → 不变量 1 锁死"动态" → 看不变量 2/3 选 Payload / PocketBase / 微信 / Next.js。
> - 要付费但只有少数章节 → 混合方案：静态站 + 付费墙（见 1.2）——鉴权仍在服务端（Access / 云函数），不违背不变量 1。
> - 不要付费 + 真理源=文件 → 不变量 1 锁死"静态" → 看不变量 3 选 Astro + Pages CMS（要网页编辑）/ Hugo / Zola（只要文件）/ Astro + Keystatic（要组件化编辑）。
> - 不要付费 + 真理源=数据库 → 罕见（静态站一般不用 DB），落到动态轻量方案。

## 一、从第一性原理出发：两类场景是不变量的推导结果

> 先读上一节「〇、第一性原理：三个不变量」。本节的两类场景，就是那三条不变量在自然约束下的**推导结果**，不是凭空划分。

本目录下所有文档，实际服务于**两个不同的项目场景**。大多数"重复内容"都源于同一套设计（权限、支付、数据模型）被两边的多个方案文档各写了一遍。所以在选型之前，必须先把场景分清楚——**场景决定技术路线，技术路线决定方案**。

| 维度 | 场景 A：AI 改编小说网 | 场景 B：小说内容付费平台 |
|------|----------------------|--------------------------|
| 目标 | 单作者保存/展示 AI 改编小说 | 多本书、收费阅读、运营推广 |
| 用户 | 1 个作者 + 只读读者 | 注册用户 + VIP + 付费读者 |
| 内容正本 | 本地 Markdown 文件 | 数据库 / CMS（正本） |
| 数据库 | ❌ 不需要 | ✅ 必需 |
| 付费/VIP/订单 | ❌ 完全没有 | ✅ 核心功能 |
| 版本管理 | ✅ Git 承担（核心需求） | 可选，数据库 + 备份 |
| 后台 | ❌ 不需要 | ✅ 运营后台（必需） |
| 内容形态 | 静态 HTML + CDN | SSR/ISR + 服务端鉴权 |
| 推荐路线 | 静态站生成器（见第二节） | 动态全栈 / 微信生态（见第三节） |

### 1.1 关键判断：为什么不能混用

**静态站生成器（Hugo / Astro / Gatsby / Eleventy）在有付费内容时存在根本矛盾：**

```text
静态站点构建流程：
1. 构建时：所有内容编译成 HTML
2. 部署后：HTML 文件直接可被访问/下载
3. 无法：按用户权限动态决定输出什么
```

付费章节一旦被预渲染进 HTML，源码里就能绕过付费墙。前端隐藏（CSS display:none）和前端 JS 校验都不安全——F12 或禁用 JS 即可看到全文。**正确的做法是服务端在请求时判断权限再返回内容，这只有动态方案能做到。**

因此：

- **要做付费/VIP → 只能走场景 B 的动态方案**，别用任何静态生成器硬撑。
- **单作者 + Markdown + 只读 + 版本管理 → 优先场景 A 的静态方案**，别为一个静态需求引入数据库和服务端。

场景 A 的原始需求（AI 改编小说网）原文：

> 改编小说网是一个基于 AI 技术的改编小说平台，利用 AI 改编著名小说。功能比较简单：只用来保存用户改编的小说（AI 创作、无需审核），要有版本管理功能。用户能很容易地使用，小说用 Markdown 保存，不需要数据库，只是文本文件。只有我一个创建者，其他用户只能查看不能编辑。界面简单，章节能关联起来方便查看管理，性能要快。最初设想用 Hugo 实现，询问是否合理、有无更好方案。

场景 B 的需求（从各方案文档归纳）：多本书（初期几本、未来上百本）、AI 自动生成、章节付费/整本购买/VIP、用户中心、管理后台、国内支付、初期个人开发、成本低运维简单。

### 1.2 中间态：混合付费与组合架构

上面两条是"铁律"，但现实有**两条不违背铁律**的中间路线——不变量 1 说的是"按人给内容必须服务端判断"，它从没说"必须整个站都动态"。

**混合付费（静态站 + 付费墙）**：付费内容只占少数几章时，可保留静态站承载 95% 免费内容，只把少数章节锁起来：

- **外部付费服务**（Memberful / Gumroad 等）：读者付款后拿到访问口令 / 凭证，锁定的章节页凭凭证可见。
- **Cloudflare Access**：免费版支持 50 个用户以内，把 `/premium/` 子路径锁在登录墙后面。
- **极小的鉴权函数**：一个云函数检查"这人付过费吗"——付了就返回正文，没付就 404。
- 代价：**无用户中心 / VIP 体系 / 订单管理**，内容被转发难以追回。适用少量付费章节，不适用完整付费平台业务。

**组合架构（静态门面 + 付费后端）**：静态站与动态平台不是只能二选一：

- **Zola / Astro 静态站 = 免费门面**：快、SEO 好、托管免费，放前几章试读导流。
- **Payload / PocketBase 平台 = 付费后端**：付费章节、支付、VIP、订单只在这里。
- 两边共享品牌、互相跳转——"免费试读引流 → 会员平台变现"是内容行业的常见打法。

> **判断**：只有少数章节收费 → **混合付费（静态为主，见 03/04）**；要正经做付费平台业务（VIP/订单/用户中心）→ **直接动态方案（文档 02）**，别在中间态上硬撑。

## 二、场景 A：静态站方案选型

### 2.1 候选方案对比

只比较与"单作者 + Markdown + 无后端"需求方向一致的方案：

| 方案 | 契合度 | 上手 | 构建速度 | 排版 | 生态 | 维护 | 总评 |
|------|--------|------|----------|------|------|------|------|
| **Hugo** | 5 | 4 | 5 | 4 | 5 | 5 | 最快上线 |
| **Astro + Pages CMS** | 5 | 4 | 4 | 5 | 5 | 5 | **综合首选** |
| Astro + Keystatic | 5 | 4 | 4 | 5 | 5 | 5 | 组件化 + 编辑 UI |
| **Zola（Rust）** | 5 | 4 | 5 | 4 | 4 | 5 | Hugo 的 Rust 平替，单文件零依赖 |
| VitePress | 4 | 5 | 5 | 4 | 4 | 5 | 适合文档风 |
| Eleventy | 5 | 3 | 4 | 3 | 3 | 4 | 灵活但配置繁 |
| mdBook / MkDocs | 3 | 5 | 5 | 3 | 3 | 5 | 偏技术手册，不适合小说 |
| Docusaurus | 3 | 4 | 3 | 4 | 4 | 4 | 太重 |
| Quartz | 2 | 3 | 3 | 4 | 2 | 3 | 数字花园范式 |
| Hexo / Jekyll | 4 | 4 | 3 | 3 | 4 | 3 | 博客范式，构建偏慢 |

### 2.2 四套主方案一句话判断

| 方案 | 适合 | 代价 |
|------|------|------|
| **Hugo + Git** | 最少折腾、最快上线（1-2 天）；纯 Markdown + Git 工作流 | 无网页编辑入口、无内容 schema 校验、阅读器交互靠模板 |
| **Astro + Pages CMS**（推荐） | 想要网页编辑后台 + 内容结构校验 + 定制阅读器，且仍然全静态 | Node 工具链较重，构建稍慢 |
| **Astro + Keystatic** | 同上，但更偏"组件化内容应用"，作者编辑 UI 由 Keystatic 提供 | 比 Pages CMS 多一点工程配置 |
| **Zola** | 同 Hugo 路线，但要 Rust 零依赖 + 更友好模板 + 链接检查内建（中文站配 Pagefind 搜索，见 04 §2.9） | 无网页编辑入口、无内置 schema 校验（需自写脚本） |

详细设计见 [03-轻量静态站架构设计.md](./03-轻量静态站架构设计.md)（Zola 备选详见 [04-Zola方案详细设计.md](./04-Zola方案详细设计.md)）。

**结论**：如果目标是"一个人创作、所有人阅读、Markdown 保存、Git 管版本、成本低、体验好"，**Astro + Pages CMS + Pagefind + GitHub + Cloudflare Pages** 是最平衡的静态方案；如果只想最快跑起来，**Hugo** 仍然干净利落；若想用 Rust 零依赖栈替代 Hugo，选 **Zola**（详见 04）。

## 三、场景 B：动态站方案选型

### 3.1 先拆需求：真正的成本在后台，不在前台

付费平台项目不是普通博客，核心需求有 6 类：内容生产与管理、阅读体验、付费与权限、后台运营、自动化（AI 批量生成）、成本与运维。**最耗时的不是前台页面，而是后台、权限、支付、内容管理和运营工具链。** 因此谁能把"后台能力"内建得更完整，谁就更接近最优方案。

### 3.2 7 类候选方案总评分

评分：5 = 很好，1 = 很差。

| 方案 | 功能 | 实现简单 | 运维 | 成本 | 支付适配 | SEO/性能 | 扩展性 | 技术风险 | 综合评价 |
|------|------|----------|------|------|----------|-----------|--------|----------|----------|
| SaaS 内容平台（小报童/知识星球） | 3 | 5 | 5 | 5 | 4 | 2 | 1 | 3 | 商业验证最强 |
| 微信生态（小程序+云开发） | 4 | 4 | 4 | 4 | 5 | 2 | 2 | 3 | 国内变现极强 |
| WordPress + 付费插件 | 4 | 4 | 3 | 4 | 4 | 3 | 3 | 3 | 传统稳妥，技术债偏多 |
| **Payload CMS 3 + PostgreSQL** | 5 | 4 | 3 | 3 | 4 | 4 | 5 | 4 | **自建综合最优** |
| PocketBase + Nuxt 3 | 3 | 5 | 4 | 5 | 4 | 4 | 3 | 3 | 低成本自建最优 |
| Next.js + Supabase | 4 | 3 | 4 | 3 | 4 | 5 | 5 | 4 | 稳健现代，但不最省事 |
| Cloudflare 全家桶 | 4 | 2 | 3 | 5 | 3 | 5 | 4 | 3 | 便宜强大，实现不简单 |

### 3.3 每类方案要点

**SaaS 内容付费平台**（小报童/知识星球/爱发电）：零开发、支付现成，最适合验证"有没有人付费、哪种付费模式"。缺点：品牌不属于自己、数据导出受限、SEO 弱、平台规则不可控。**商业验证最优，不是长期品牌建设最优。**

**微信生态**（公众号付费阅读 / 小程序+云开发）：国内支付链路最自然、转化通常优于独立站、微信登录零门槛。缺点：SEO 几乎没有、平台规则与审核强约束、与 Web 生态复用性差。**适合中文用户移动端首发，不适合作为搜索型内容站唯一主阵地。**

**WordPress**：后台、文章管理、SEO 插件成熟，非技术运营者上手快。缺点：插件堆叠有性能/兼容债，小说"章节+进度+多级权限"场景仍需大量定制，AI 自动化不如现代全栈顺滑。**适合传统内容站运营。**

**Payload CMS 3 + PostgreSQL**：后台、内容模型、权限、上传、草稿/发布、Hooks/Jobs 全部内建，AI 工作流好接，前台仍可用 Next.js。缺点：仍需 PostgreSQL，部署不如 PocketBase 轻。**长期品牌站、运营后台强时最值得优先评估。**

**PocketBase + Nuxt 3**：单二进制自带 SQLite + Auth + 后台 + 文件存储 + API，一台低配 VPS 即可运行。缺点：SQLite 高并发/复杂事务不如 PostgreSQL，社区规模小，规模大了要迁移。**个人开发者低成本 MVP 首选。**

**Next.js + Supabase**：前台 SEO/SSR 强、Supabase 提供 Auth/DB/Storage、社区大。缺点：后台要自己写、权限要跨中间件/API/RLS 多层实现、支付状态机全自己搭——"工程化搭积木"，不是"最省事的内容平台"。**适合熟悉这套栈、要长期自由度的人。**

**Cloudflare 全家桶**（Workers + D1 + R2 + KV）：基础设施成本极低、全球边缘分发强、R2 无出网费。缺点：复杂度常被低估，D1 在订单/事务一致性上要谨慎设计，Workers runtime 限制多。**适合技术导向团队，不适合当前阶段追求简单落地。**

### 3.4 最终推荐排序

结合项目目标（多本书、AI 生成、章节付费/VIP、用户中心、管理后台、初期个人开发、低成本运维）：

| 优先级 | 方案 | 什么时候选它 |
|--------|------|--------------|
| **第一推荐** | **Payload CMS 3 + PostgreSQL** | 明确要做长期品牌站、看重后台和内容运营效率、不想重复造 CMS 轮子 |
| **第二推荐** | **PocketBase + Nuxt 3** | 低成本独立站 MVP、技术尽量简单、能接受中后期迁移 |
| **第三推荐** | Next.js + Supabase（**删减复杂度**） | 最熟悉这套栈、愿承担工程装配、要长期自由度 |
| 国内移动端首发 | 微信小程序 + 云开发 | 受众是中文移动端用户、最看重支付转化、先验证市场 |
| 纯商业验证 | SaaS / 微信生态 | 还没证明题材能变现、不想先投入数周开发 |

> **如果继续用 Next.js + Supabase，务必删减：先不要上 Meilisearch（用数据库模糊搜索）；先不要坚持 Markdown 为唯一正本（以数据库为正本更简单）；先不做完整管理后台（最小后台即可）；先只做单章付费或 VIP 二选一，别四种支付模型全开。**

### 3.5 决策原则速查

- 选 **SaaS/微信生态**：目标是验证市场、最关心支付转化和发布速度、能接受平台约束。
- 选 **Payload CMS 3**：目标是长期品牌站、很在意后台管理、不想从零写 CMS、希望以后加 AI 流程/审核/推荐位。
- 选 **PocketBase + Nuxt**：目标是低成本独立站、技术尽量简单、能接受中后期迁移。
- 继续 **Next.js + Supabase**：最熟悉这套栈、愿承担更多工程装配、要长期自由度。
- 选 **微信小程序**：中文移动端用户、微信内完成阅读/登录/支付、接受平台审核约束。

## 四、推荐的演进路线

### 4.1 场景 B（付费平台）

```text
路线 1（最务实）：
阶段 1：SaaS / 微信生态验证题材
阶段 2：PocketBase + Nuxt 3 做独立站 MVP
阶段 3：收入稳定后迁移到 Payload CMS 3

路线 2（直接做长期站）：
阶段 1：Payload CMS 3 + PostgreSQL + Payjs
阶段 2：补搜索、评论、阅读进度
阶段 3：接 AI 生成工作流、推荐系统、运营活动

路线 3（坚持现有技术偏好）：
阶段 1：Next.js + Supabase（只做最小付费闭环）
阶段 2：补后台与内容工作流
阶段 3：补搜索、推荐、自动化
```

### 4.2 场景 A（静态站）

```text
阶段 1：Astro + Pages CMS（或 Hugo / Zola）跑通「写作 -> 构建 -> 发布 -> 阅读」
阶段 2：补阅读体验（字号/暗色/目录抽屉）、Pagefind 搜索、版本说明页
阶段 3：若未来出现付费/用户需求，才迁移到场景 B 的动态方案
```

## 五、一句话总判断

- **场景 A（静态单作者站）**：默认 **Astro + Pages CMS**，最快上线用 **Hugo**（或 Rust 平替 **Zola**）。
- **场景 B（付费平台）**：长期主站选 **Payload CMS 3 + PostgreSQL**，低成本 MVP 选 **PocketBase + Nuxt 3**，中文移动端首发选 **微信小程序**，纯商业验证用 **SaaS/微信生态**。
- **中间态**：只有少数章节收费 → **静态站 + 付费墙**（见 1.2）；"免费引流 + 付费变现" → **静态门面 + 付费后端组合**（见 1.2）；完整成本对比见第六节。

## 六、统一 TCO 成本对照

选型除了看能力，还要看**总拥有成本（TCO）**。下表把静态 / 动态各方案的年成本并排（个人开发者规模，2026-08 时点，粗略量级）：

| 方案 | 托管 | 数据库 | 支付 | 月成本(约) | 主要隐性成本 |
|------|------|--------|------|-----------|--------------|
| 静态站（Hugo / Zola / Astro） | Cloudflare Pages 免费层 | 无 | 无 | **¥0**（仅域名 ~¥60/年） | 无服务器运维；要收费只能混合方案 |
| PocketBase + Nuxt 3 | 1 台小 VPS | 自带 SQLite | Payjs 等 | ¥20–50 | VPS 维护、备份、升级 |
| Payload CMS 3 + PostgreSQL | VPS / Render / Fly | 生产级 PG | Payjs 等 | $10–30 + PG | 备份、监控、迁移、扩 PG |
| 微信小程序 + 云开发 | 云开发按量 | 云数据库 | 微信支付 | ¥0–几十（按量） | 微信审核/规则、订阅消息 |
| SaaS / 微信生态 | 平台托管 | 平台 | 平台内 | 抽成 | 数据在平台、品牌不独立 |

> **结论**：静态 ≈ **0 成本**，动态方案的月费本质是"数据库 + 服务器 + 后台"的代价。**只要付费业务规模还不足以覆盖这笔钱，混合付费（1.2）就是更理性的中间态。** 具体选型回到第〇节决策树——成本是决策树的隐性约束之一。
