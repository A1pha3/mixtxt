# 动态付费平台架构设计（场景 B）

> 文档类型：动态小说内容付费平台架构设计合集
>
> 适用场景：多本书、AI 自动生成、章节付费 / 整本购买 / VIP、用户中心、管理后台、国内支付。
>
> 本方案对应选型结论（见 [01-需求与方案选型.md](./01-需求与方案选型.md) 第五节）：

> - **方案 B：Next.js + Supabase**（第三推荐，工程化路线）
> - **方案 C：微信小程序 + 云开发**（中文移动端首发）
> - **方案 D：PocketBase + Nuxt 3**（低成本 MVP）

## 第一部分：共享核心设计（所有动态方案通用）

以下设计在任何动态方案中都成立。各方案只是"用不同的技术实现同一套规则"。**先读完这部分，再去看具体方案，可避免重复理解。**

### 1.1 数据模型核心概念

各方案共享以下核心数据概念（字段名因技术栈略有差异）：

| 概念 | 说明 | 关键字段 |
|------|------|----------|
| users | 用户、VIP 状态、角色 | `role`（user/editor/admin）、`vipExpiresAt` |
| books | 书籍元数据、定价 | slug、title、status、isPaid、price、chapterPrice |
| chapters | 章节元数据与正文 | book、order、content、isVIP、status、wordCount |
| purchases | 所有付费行为主记录 | purchaseType（book/chapter/vip/recharge）、amount、status |
| recharges | 充值流水（衍生表） | user、amount、paymentNo、status |
| vipSubscriptions | VIP 订阅记录 | plan、startsAt、expiresAt、status |
| readingProgress | 阅读进度 | user、book、chapter、lastPosition |
| comments | 评论（可后置） | user、book、chapter、parent、content |
| bookLikes / chapterLikes | 点赞（可后置） | user、target |

**设计要点：**

- **purchases 是唯一交易主表**：所有付费行为（单章/整本/VIP/充值）统一进 purchases，recharges 与 vipSubscriptions 只是衍生流水/订阅状态表。支付回调只需查一张表。
- **用户角色表（users）与权限判断分离**：`role` 只用于后台权限（user/editor/admin）；VIP 是订阅状态，通过 vipSubscriptions 或 vipExpiresAt 推导，不存进 role。
- 书籍/章节状态枚举：`planning/serializing/completed/paused`、`draft/review/published/archived`。

### 1.2 权限设计

**VIP 状态 vs 后台角色：**

- **VIP 是订阅状态，不是角色**。通过 `vip_subscriptions` 表推导，不存储在 `role` 字段。
- `role` 仅用于后台权限控制：`user / editor / admin`。
- 管理员（admin）可以同时拥有 VIP 订阅，两个维度互不干扰。

**章节访问判断（统一封装为一个服务函数）：**

```text
canUserAccessChapter(user, chapter, book)：
1. 章节不是 VIP（免费）          -> 直接可看
2. 用户未登录                    -> 不可看
3. 用户购买过该章节              -> 可看
4. 用户购买过整本书              -> 可看
5. 用户存在有效 VIP 订阅         -> 可看
6. 否则                          -> 不可看（显示付费墙）
```

**安全铁律：不要把正文权限只交给前端。** 前端隐藏按钮、隐藏跳转都不是安全控制。真正的权限控制必须在：

- 服务端页面渲染前
- API 返回正文前
- 下载 / 导出正文前

统一做判断。付费正文只能在服务端拿到后再渲染，永远不要 props 进 Client Component（会出现在 RSC payload 中）。

### 1.3 支付系统设计

**支付目标（首发最小闭环）：** 充值、单章购买、整本购买、VIP 开通。**首发建议只做两种：单章购买 + VIP 开通**（或 VIP 二选一），不要一开始把四种支付模型全开，否则状态机会明显变复杂。

**标准流程：**

```text
用户点击购买
  -> 服务端创建订单（status=pending）
  -> 返回支付链接 / 拉起支付
  -> 用户完成支付
  -> 支付平台回调（webhook）
  -> 服务端验签
  -> CAS 更新 pending -> completed
  -> 根据订单类型执行后续动作（开 VIP / 加余额 / 记流水）
  -> 前端刷新状态
```

**幂等性要求（必须满足）：**

- 重复回调不会重复加余额 / 重复开 VIP / 多次创建流水。
- `paymentNo` 唯一。
- **只允许更新 `status = 'pending'` 的记录（CAS 模式）**，即使并发 webhook 重试，数据库行锁保证只有一个能成功。
- 所有衍生动作都在"订单成功转 completed 后"执行一次。

**为什么订单表必须是主凭证：** 因为最终"你是否有权阅读"不是 UI 决定的，而是交易事实决定的。买了章节/整本/开了 VIP 都有服务端可追溯的凭证。

**核心安全规则：权限开通只认服务端支付回调，不认前端状态；余额操作使用原子数据库函数（SECURITY DEFINER），不在应用层分步扣款 + 写单。**

### 1.4 AI 内容生产工作流

```text
AI 生成章节草稿
  -> 写入内容库（status=draft, isAIGenerated=true）
  -> 人工修订（质量不稳定、文风易漂移、平台审核要求真实存在）
  -> 发布（status=published）
  -> 触发 afterChange Hook：
     - 更新 books.chapterCount / wordCount
     - 刷新缓存 / revalidatePath
     -（后期）同步搜索索引
```

> **AI 负责生成草稿，人来负责决定是否发布。** 自动发布风险很高，尤其微信生态有内容审核。

### 1.5 内容正本策略（选定一种后保持一致，不要混用）

| 方案 | 内容正本 | 说明 |
|------|----------|------|
| Next.js 方案 | 本地 Markdown 文件为正本 | 数据库存元数据索引；适合 Git 工作流 |
| Payload CMS 方案 | CMS / 数据库为正本 | Markdown 仅作导出格式；适合运营工作流 |

### 1.6 通用安全清单

1. 付费正文只在服务端读取后渲染。
2. 支付结果只认 webhook，不认前端轮询结果。
3. 后台权限与前台用户权限分离。
4. 订单、余额、VIP 不能让客户端直接写（客户端只开 SELECT）。
5. 每种支付回调都必须幂等（CAS）。
6. 每个 SECURITY DEFINER 函数显式 `SET search_path`（防 search_path 注入）。
7. service role key 永不出现在 `NEXT_PUBLIC_` 变量中。
8. 数据库每日备份；定期对账 `purchases.status='completed'` 与支付平台流水。

## 第二部分：方案 A — Payload CMS 3 + PostgreSQL（第一推荐）

### 2.1 为什么选它

项目真正复杂的部分不在首页/书籍页/章节页，而在内容建模、发布状态与后台管理、权限与访问控制、订单充值 VIP、AI 生成后的人工修订发布流。Payload CMS 本身就是为这些能力设计的，**后台和内容模型开箱即用**：

| 对比项 | Next.js + Supabase | Payload CMS 3 |
|--------|-------------------|---------------|
| 后台管理 | 需要自己开发 | ✅ 内建 Admin |
| 内容模型 | 需自己定义 API + UI | ✅ Collection / Globals 开箱即用 |
| 草稿/发布 | 需自研 | ✅ 原生支持 draft/version |
| 富文本/媒体管理 | 需自己接 | ✅ 原生支持 |
| 权限控制 | 中间件 + API + RLS 多层拼装 | ✅ Access Control 集中管理 |
| 生命周期 Hook | 需自己拼 | ✅ beforeChange / afterChange / jobs |

**内容正本策略：Payload 为唯一内容正本。** 编辑、运营、AI 工作流都围绕 CMS 运作；章节修改后立即生效，无需 Markdown/DB 双写同步；Markdown 保留为"导出能力"即可（导出 JSON / Markdown ZIP / 自动备份）。

### 2.2 技术栈与部署

| 层级 | 选型 |
|------|------|
| Web 框架 | Payload CMS 3（基于 Next.js 15） |
| 数据库 | PostgreSQL |
| 认证 | Payload Auth / 用户 Collection |
| 文件存储 | S3 / Cloudflare R2 |
| 支付 | Payjs（初期） |
| 搜索 | Meilisearch（后期，非首发依赖） |
| 部署 | Railway / Fly.io / VPS + Docker |
| 定时任务 | Payload Jobs / 外部 Cron |

**首发部署模式（简单稳妥）：** Payload App（前台+Admin+API）+ PostgreSQL + R2/S3 + Payjs。Meilisearch 不应成为首发必需依赖。

### 2.3 渲染策略

| 页面 | 渲染模式 | 说明 |
|------|----------|------|
| 首页 / 书籍列表 | SSG / ISR | 内容稳定，适合缓存 |
| 书籍详情 / 免费章节 | ISR | 可缓存，兼顾 SEO |
| 付费章节 | SSR / Dynamic | 逐请求校验访问权限 |
| 用户中心 / 书架 | SSR | 个性化数据 |
| Admin 后台 | Payload Admin | 内建，无需自研 |
| API / Webhook | Server | 支付、评论、进度、购买接口 |

### 2.4 Collection 设计

| Collection | 用途 |
|------------|------|
| users | 用户、作者、管理员、VIP 状态 |
| books | 书籍信息 |
| chapters | 章节正文与元数据 |
| categories / tags | 分类 / 标签 |
| purchases | 所有付费行为主记录 |
| recharges | 充值流水 |
| vipSubscriptions | VIP 订阅记录 |
| comments | 评论 |
| readingProgress | 阅读进度 |
| bookLikes / chapterLikes | 点赞（可后置） |
| banners / featuredBooks | 首页推荐位（可选） |

**users 建议字段：** email、username、avatar、bio、`role`（user|editor|admin）、`isVIP`、`vipExpiresAt`、`balance`、`status`（active|banned）、lastLoginAt。VIP 通过 `isVIP + vipExpiresAt` 或 vipSubscriptions 推导，不用 role 表达。

**books 建议字段：** slug、title、subtitle、authorName、cover、description、`status`（serializing|completed|paused）、isPaid、price、chapterPrice、categories、tags、wordCount、chapterCount、isPublished、publishedAt、seoTitle、seoDescription、featured、sortOrder。

**chapters 建议字段：** book（relation）、slug、title、chapterOrder、content（richText/markdown）、excerpt、isVIP、priceOverride（可选）、`status`（draft|scheduled|published|archived）、publishedAt、scheduledAt、wordCount、isAIGenerated、aiModel、aiPromptVersion、viewCount、likeCount。AI 流水线直接生成 markdown 时可用 `textarea + markdown renderer` 简单模式，后期升级富文本。

**purchases（交易主表）：** user、`purchaseType`（chapter|book|vip|recharge）、book（可空）、chapter（可空）、amount、paymentMethod（wechat|alipay|balance）、paymentNo、`status`（pending|completed|failed|refunded）、completedAt、meta（JSON，套餐/活动信息）。

**vipSubscriptions：** user、`plan`（monthly|yearly|lifetime）、amount、startsAt、expiresAt、status、paymentNo。

**comments：** user、book、chapter、parent、content、`status`（visible|hidden|deleted|pendingReview）、likeCount。

**readingProgress：** user、book、chapter、progressPercent、lastPosition、updatedAt。

### 2.5 权限设计（Payload Access Control）

后台角色：user（无后台权限） / editor（可编辑书籍章节、审核评论，不能处理资金） / admin（全权限）。

前台章节访问用统一服务函数 `canUserAccessChapter(user, chapter, book)`（见 1.2 节判断顺序）。

### 2.6 支付系统

同第一部分 1.3。Payload 中建议：

- `paymentNo` 唯一；CAS 更新 `status=pending -> completed`。
- `afterChange` Hook：当 purchases 状态从 pending 变 completed 时触发后续动作（开 VIP / 加余额 / 记流水）。

### 2.7 Hooks 与 Jobs

- books/chapters `beforeChange`：校验 slug、自动补齐字数。
- books/chapters `afterChange`：更新章节数、刷新缓存、同步搜索索引。
- purchases `afterChange`：pending -> completed 触发后续动作。
- Jobs：AI 批量生成章节、定时发布草稿、清理失效订单、导出备份、同步 Meilisearch。

## 第三部分：方案 B — Next.js + Supabase（工程化路线）

### 3.1 为什么从 Astro 切换到 Next.js

| 问题（Astro 方案） | 严重程度 | 说明 |
|------|----------|------|
| SSG + 付费墙矛盾 | 🔴 致命 | 付费章节内容构建时写入 HTML，源码可绕过付费墙 |
| 全站重建 | 🔴 严重 | 每次内容更新需全站 SSG 重建，上百本书时构建极慢 |
| 动态交互弱 | 🟡 中等 | 岛屿架构削弱 SSG 性能优势，管理后台体验差 |
| Content Collections 未利用 | 🟡 中等 | 从数据库读内容而非本地 Markdown，浪费 Astro 核心功能 |

Next.js App Router 的优势：付费内容保护（RSC 服务端渲染）、ISR 按需再生、RSC + Client Components 自然混合、middleware.ts 统一认证、Route Handlers 原生支持支付 Webhook、同一项目中做管理后台。

### 3.2 技术栈

| 层级 | 选型 | 理由 |
|------|------|------|
| 前端框架 | Next.js 15（App Router） | RSC + ISR + Server Actions |
| 后端服务 | Supabase | PostgreSQL + Auth + Storage |
| 数据库 | Supabase PostgreSQL | 500MB 免费额度，RLS 权限控制 |
| 认证 | Supabase Auth | @supabase/ssr 处理 SSR cookie |
| 文件存储 | Supabase Storage | 封面、图片 |
| 搜索 | Meilisearch | 中文友好；注：非 Supabase 官方集成，需独立部署或 Meilisearch Cloud |
| 支付 | Payjs（初期）/ 微信支付宝直连（后期） | 国内支付，个人可用 |
| 部署 | Vercel | Next.js 原生支持，免费层 |
| 样式 | Tailwind CSS + shadcn/ui | 开发效率高 |

### 3.3 架构与渲染策略

```text
本地开发环境（content/ Markdown 正本 + meta.json）-> Git push
  -> GitHub 仓库（代码+内容版本控制，GitHub Actions 自动化）
  -> Supabase（PostgreSQL 用户/订单/章节元数据索引 + Auth + Storage + Meilisearch）
  -> Vercel（SSG 首页/列表/免费章节；SSR 付费章节权限校验；ISR 书籍详情；API 支付/评论/管理）
  -> Payjs / 微信支付宝（扫码支付、Webhook 回调）
```

| 页面 | 渲染模式 | 说明 |
|------|----------|------|
| 首页、书籍列表 | SSG | 构建时生成，CDN 缓存 |
| 书籍详情 | ISR | revalidate: 3600 |
| 免费章节 | ISR | revalidate: 600 |
| 付费章节 | SSR | 服务端实时校验权限，内容不缓存 |
| 用户中心 | SSR | 需要认证 |
| 管理后台 | CSR | 大量交互 |
| API 路由 | Server | Route Handlers 处理支付回调等 |

### 3.4 数据库设计（关键差异点）

1. **chapters 表不存 content 字段**：内容从本地 Markdown 构建时读取，数据库只存元数据和索引。
2. 修复 balances 表 RLS 漏洞：禁止用户直接 UPDATE 余额。
3. deduct_balance 使用原子操作，避免竞态。
4. 移除 PostgreSQL 中文全文搜索（zhparser 配置门槛高），改用 Meilisearch。
5. **purchases 表统一记录所有付费行为**：`purchase_type` 区分 chapter/book/vip/recharge；recharges 与 vip_subscriptions 是衍生表。

#### 用户相关

```sql
CREATE TABLE user_profiles (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  username TEXT UNIQUE,
  avatar_url TEXT,
  bio TEXT,
  role TEXT DEFAULT 'user' CHECK (role IN ('user', 'editor', 'admin')),
  vip_expires_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE balances (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID UNIQUE REFERENCES auth.users(id) ON DELETE CASCADE,
  balance DECIMAL(10, 2) DEFAULT 0.00 CHECK (balance >= 0),
  total_recharged DECIMAL(10, 2) DEFAULT 0.00,
  total_spent DECIMAL(10, 2) DEFAULT 0.00,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

ALTER TABLE balances ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can view own balance"
  ON balances FOR SELECT USING (auth.uid() = user_id);
-- 注意：不设 INSERT/UPDATE/DELETE 策略，余额变更只允许通过 SECURITY DEFINER 函数（add_balance/deduct_balance）操作
-- 初始余额行由 handle_new_user 触发器创建
```

#### 书籍相关

```sql
CREATE TABLE books (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  slug TEXT UNIQUE NOT NULL,
  title TEXT NOT NULL,
  author_id UUID REFERENCES auth.users(id),
  author_name TEXT NOT NULL,
  cover_url TEXT,
  description TEXT,
  status TEXT DEFAULT 'serializing' CHECK (status IN ('serializing', 'completed', 'paused')),
  is_paid BOOLEAN DEFAULT FALSE,
  price DECIMAL(8, 2) DEFAULT 0.00,
  chapter_price DECIMAL(8, 2) DEFAULT 0.00,
  view_count INTEGER DEFAULT 0,
  like_count INTEGER DEFAULT 0,
  chapter_count INTEGER DEFAULT 0,
  meta_title TEXT,
  meta_description TEXT,
  is_published BOOLEAN DEFAULT FALSE,
  is_deleted BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE chapters (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  book_id UUID NOT NULL REFERENCES books(id) ON DELETE CASCADE,
  slug TEXT NOT NULL,
  title TEXT NOT NULL,
  local_file_path TEXT NOT NULL,        -- 正文在本地 Markdown，数据库只存路径
  word_count INTEGER DEFAULT 0,
```

### 3.6 数据库函数（余额原子操作）

```sql
-- 新用户初始化
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO public.user_profiles (id) VALUES (NEW.id);
  INSERT INTO public.balances (user_id) VALUES (NEW.id);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = public;
CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();

-- 章节数统计
CREATE OR REPLACE FUNCTION update_book_chapter_count()
RETURNS TRIGGER AS $$
BEGIN
  UPDATE books
  SET chapter_count = (
    SELECT COUNT(*) FROM chapters
    WHERE book_id = COALESCE(NEW.book_id, OLD.book_id)
      AND is_published = true AND is_deleted = false
  ), updated_at = NOW()
  WHERE id = COALESCE(NEW.book_id, OLD.book_id);
  RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = public;
CREATE TRIGGER on_chapter_change
  AFTER INSERT OR UPDATE OR DELETE ON chapters
  FOR EACH ROW EXECUTE FUNCTION update_book_chapter_count();

-- 充值：UPSERT 避免余额行不存在
CREATE OR REPLACE FUNCTION add_balance(p_user_id UUID, p_amount DECIMAL)
RETURNS VOID AS $$
BEGIN
  IF p_amount <= 0 THEN RAISE EXCEPTION 'Amount must be positive'; END IF;
  INSERT INTO balances (user_id, balance, total_recharged)
  VALUES (p_user_id, p_amount, p_amount)
  ON CONFLICT (user_id) DO UPDATE
  SET balance = balances.balance + EXCLUDED.balance,
      total_recharged = balances.total_recharged + EXCLUDED.total_recharged,
      updated_at = NOW();
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = public;

-- 扣款：原子 UPDATE + 余额检查
CREATE OR REPLACE FUNCTION deduct_balance(p_user_id UUID, p_amount DECIMAL)
RETURNS BOOLEAN AS $$
DECLARE affected INTEGER;
BEGIN
  IF p_amount <= 0 THEN RAISE EXCEPTION 'Amount must be positive'; END IF;
  UPDATE balances
  SET balance = balance - p_amount, total_spent = total_spent + p_amount, updated_at = NOW()
  WHERE user_id = p_user_id AND balance >= p_amount;
  GET DIAGNOSTICS affected = ROW_COUNT;
  RETURN affected = 1;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = public;

-- 原子余额购买：单事务完成扣款 + 创建订单，避免中间状态
CREATE OR REPLACE FUNCTION purchase_with_balance(
  p_user_id UUID, p_purchase_type TEXT, p_book_id UUID, p_chapter_id UUID, p_amount DECIMAL
)
RETURNS TABLE (success BOOLEAN, purchase_id UUID) AS $$
DECLARE v_deducted BOOLEAN; v_purchase_id UUID;
BEGIN
  IF p_amount <= 0 THEN RAISE EXCEPTION 'Amount must be positive'; END IF;
  v_deducted := deduct_balance(p_user_id, p_amount);
  IF NOT v_deducted THEN RETURN QUERY SELECT false, NULL::UUID; RETURN; END IF;
  INSERT INTO purchases (user_id, purchase_type, book_id, chapter_id, amount, payment_method, status, completed_at)
  VALUES (p_user_id, p_purchase_type, p_book_id, p_chapter_id, p_amount, 'balance', 'completed', NOW())
  RETURNING id INTO v_purchase_id;
  RETURN QUERY SELECT true, v_purchase_id;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER SET search_path = public;
```

```typescript
// src/lib/payment.ts
import crypto from 'crypto'
const config = { mchid: process.env.PAYJS_MCHID!, key: process.env.PAYJS_KEY! }

export function createPayjsUrl(params: { total_fee: number; out_trade_no: string; body: string; notify_url: string; type?: 'wechat' | 'alipay' }): string {
  const data: Record<string, string> = {
    mchid: config.mchid,
    total_fee: String(params.total_fee),
    out_trade_no: params.out_trade_no,
    body: params.body,
    notify_url: params.notify_url,
    type: params.type || 'wechat',
  }
  data.sign = signParams(data)
  return `https://payjs.cn/api/cashier?${new URLSearchParams(data).toString()}`
}

export function verifyNotify(params: Record<string, string>): boolean {
  const sign = params.sign
  delete params.sign
  return sign === signParams(params)
}

function signParams(params: Record<string, string>): string {
  const sorted = Object.keys(params).filter(k => params[k] !== '').sort()
    .map(k => `${k}=${params[k]}`).join('&')
  return crypto.createHash('md5').update(sorted + `&key=${config.key}`).digest('hex').toUpperCase()
}
```

**创建订单（/api/payment/create）**：余额购买走 `supabase.rpc('purchase_with_balance')`（原子扣款+建单）；外部支付先生成 outTradeNo，**检查重复 pending 订单**（PostgREST 中 NULL 比较必须用 `.is()` 不能用 `.eq()`），复用已有 pending 单号或插入新单，再返回 Payjs 收银台 URL。

## 第四部分：方案 C — 微信小程序 + 云开发（中文移动端首发）

### 4.1 结论与适用判断

**微信小程序非常适合作为"国内中文用户的首发阅读和付费产品"，但不是全网内容站的唯一终局。**

适合（满足 ≥3 条）：用户主要是中文移动端读者；最看重支付转化而非 SEO 流量；希望减少账号/支付系统复杂度；还没有成熟独立站；想先做 MVP 验证题材和付费模式。

**新手最容易的误判**：小程序"看上去像前端项目"，但本质是"平台产品 + 平台规则 + 平台能力"的组合——微信登录、类目、审核、订阅消息、微信支付、云开发、数据合规与内容审核都要接。

**首发功能范围**：用户侧（首页推荐/最近更新/分类、书籍详情、章节阅读、微信一键登录、单章付费或 VIP、用户中心：书架/购买记录/VIP/进度）；管理侧（书籍/章节管理、发布下架、订单查看、用户查看）；内容生产侧（手动录入、AI 生成草稿、人工审核后发布）。**后置：评论、举报、积分、勋章、多作者协作、章节全文搜索、推荐算法。**

### 4.2 资质准备（最容易卡住新手）

**必备账号：** 微信公众平台小程序账号（记 AppID + 管理员权限）、小程序开发者权限、微信开发者工具、微信云开发环境。**做支付还需要：微信商户号 / 微信支付能力 + 经营类目与支付场景匹配。**

**三大坑：** ① 注册了小程序不等于能直接收钱（还涉及主体资质、商户号开通、类目匹配、审核）；② "电子书/小说"不是想卖就卖（内容合规、敏感题材、服务说明和用户协议）；③ 先写了很多功能最后卡在审核——正确顺序是：先确认类目与业务形态可行 → 再做首发闭环 → 再逐步扩功能。

### 4.3 架构

```text
微信小程序客户端（首页/书籍页/章节页/用户中心/书架）
  -> 微信云开发层（云数据库 books/chapters/users/orders/vip/progress/bookshelf
                   云函数 登录补全/创建订单/支付回调/权限校验
                   云存储 封面/插图/富媒体）
  -> 内容后台 / AI 生产流（简单 Admin Web / Payload CMS / 导入脚本）
```

**为什么推荐"云开发 + 简单后台"：** 新手一开始就做小程序前端 + 自建后端 + 自建数据库 + 自建登录 + 自建支付后端 + 自建后台会非常重。云开发让你先跑起来：不用先买服务器、搭登录系统、配 API Gateway。**但云开发不是"零成本无限后端"**——复杂查询有限、大规模搜索不强、长期架构自由度不如自建后端，适合做首发版的"平台内后端"。

### 4.4 数据模型（逻辑模型，云开发集合或后端数据库均适用）

- **users**：openid（核心唯一标识）、unionid（可选）、nickname、avatarUrl、gender、`role`（user|admin|editor）、isVIP、vipExpiresAt、balance、createdAt、lastLoginAt。**不要把 VIP 只写成 role。**
- **books**：bookId、title、subtitle、authorName、coverUrl、description、`status`（serializing|completed|paused）、isPaid、price、chapterPrice、categoryIds、tagNames、wordCount、chapterCount、isPublished、publishedAt、sortOrder、featured。
- **chapters**：chapterId、bookId、title、chapterOrder、content、excerpt、isVIP、priceOverride、`status`（draft|published|archived）、publishedAt、wordCount、isAIGenerated、aiModel。首发正文直接用字符串存储即可。
- **orders**（交易主表）：orderId、userId、`orderType`（chapter|book|vip|recharge）、bookId、chapterId、amount、payMethod、transactionId、`status`（pending|paid|failed|refunded）、createdAt、paidAt。
- **vipSubscriptions**：subscriptionId、userId、`plan`（monthly|yearly|lifetime）、amount、startsAt、expiresAt、status、orderId。
- **bookshelf**：userId、bookId、addedAt、lastReadChapterId、lastReadAt。
- **readingProgress**：userId、bookId、chapterId、progressPercent、lastPosition、updatedAt。
- **comments**（可后置）：commentId、userId、bookId、chapterId、content、status、createdAt。

### 4.5 登录与用户体系

小程序天然适合微信登录，建议流程：触发登录 → 拿临时登录凭证 → 云函数换 openid → 按 openid 查用户 → 不存在则创建 → 返回用户资料与登录态。省掉注册表单/密码找回/邮箱验证。**登录态要统一从服务端/云开发侧管理，不要只靠前端缓存判断。**

### 4.6 内容权限与支付

- 章节访问规则同 1.2 节判断顺序。**不要只靠前端隐藏正文**——小程序请求云函数/后端接口，云函数判断权限，有权限才返回正文。
- 支付模型首发二选一：**只做 VIP**（最简单、状态清晰、审核好解释）或**只做单章购买**（更贴近按章付费、用户门槛低）。新手优先建议先做 VIP。支付流程、幂等规则同 1.3 节。**权限开通只认服务端支付成功回调。**

### 4.7 内容后台与审核上线

- 内容后台三阶段：先用导入脚本+表格维护 → 做一个简单 Web 后台（书籍增删改下架、章节编辑发布、订单查看、用户查看）→ 接入成熟 CMS（Payload/Directus）。**小程序不适合承担复杂后台，后台用 Web 做。**
- 微信生态审核注意：内容合规、介绍文案合规、功能描述清晰、支付与服务描述一致、用户协议/隐私政策/客服信息完整；小说内容避免明显违规题材、擦边描述、风险封面简介；首版提交审核功能要清晰克制（首页/书籍列表/阅读/VIP 或章节购买/用户中心）。
- 上线顺序：注册配置小程序 → 创建云开发环境 → 首页/书籍页/阅读页 → 微信登录 → 最小权限控制 → 支付闭环 → 补齐协议/隐私/客服 → 体验版测试 → 邀请测试用户 → 修复 → 提交审核 → 发布。**先给几个人真实使用体验版，不要直接冲审核。**

### 4.9 开发路线图

- Phase 1 最小阅读闭环（1 周）：小程序初始化、云开发环境、书籍/章节集合建模、首页/详情/阅读页、微信登录、免费章节阅读。
- Phase 2 付费闭环（1 周）：订单集合、VIP 或单章付费、支付接口、服务端回调、权限校验。
- Phase 3 用户能力（1 周）：书架、阅读进度、购买记录、VIP 页面。
- Phase 4 内容生产（1 周）：导入脚本、AI 草稿生成、简单后台/内容发布。
- Phase 5 增强（后续）：评论、推荐位运营、搜索、公众号联动、Web 官网联动。

### 4.10 从零初始化教程（最小可运行版本）

> 本节目标是"先跑起来"：不做登录/付费/权限/后台，只打通「云数据库 -> 首页书籍列表 -> 书籍详情 -> 章节阅读」。

**① 准备与注册**：微信公众平台注册小程序（记 AppID）；安装微信开发者工具（扫码登录）；本地装 VS Code、Git、Node.js。现阶段不需要：支付商户号、正式域名、服务器、自建数据库。

**② 新建项目**：开发者工具 -> 新建小程序项目 -> 项目目录（如 `~/projects/miniprogram-novel`）-> AppID -> 后端服务选"微信云开发"-> 语言 JavaScript。

**③ 认识结构**：`miniprogram/`（前端，.wxml 结构 / .wxss 样式 / .js 逻辑 / .json 配置）、`cloudfunctions/`（云函数）、`project.config.json`。**第一步不要上 Taro/TypeScript/状态管理，目标只有一个：把书籍列表从云数据库读出来显示在页面上。**

**④ 开通云开发**：创建环境，建议命名 `novel-dev` / `novel-test` / `novel-prod`（首发一个 dev 足够）。在 `miniprogram/app.js` 初始化：

```javascript
App({
  onLaunch() {
    if (!wx.cloud) { console.error('请使用支持云开发的基础库'); return }
    wx.cloud.init({ env: 'novel-dev', traceUser: true })  // env 换成你的环境 ID
  },
})
```

**⑤ 建集合与示例数据**：只建 `books` 和 `chapters` 两个集合（先不加价格/订单/AI 字段）。

```json
// books 集合：1 条

  "bookId": "book-001",
  "title": "星海边缘",
  "authorName": "林舟",
  "coverUrl": "https://images.unsplash.com/photo-1512820790803-83ca734da794?auto=format&fit=crop&w=400&q=80",
  "description": "一名普通维修员，被卷入星际文明边界的巨大谜团。",
  "status": "serializing",
  "isPublished": true,
  "chapterCount": 2,

// chapters 集合：2 条

  "content": "凌晨四点，旧港口的维修灯还亮着。陈默弯着腰，正给一艘退役运输船更换动力管线。……",
  "isVIP": false, "status": "published", "createdAt": "2026-04-28T10:00:00.000Z" }
```

**⑥ 首页**：`app.json` 配置 `pages/home/home` 为首页；`home.js` 查询 `db.collection('books').where({isPublished: true}).orderBy('sortOrder','asc').get()`，`home.wxml` 用 `wx:for` 渲染书籍卡片，`home.wxss` 写卡片样式。点击卡片 `wx.navigateTo('/pages/book-detail/book-detail?bookId=...')`。

**⑦ 书籍详情页**：`book-detail.js` 并行加载 book + chapters（`where({bookId, status:'published'}).orderBy('chapterOrder','asc')`），模板渲染章节列表（`isVIP` 显示 VIP 角标）。

**⑧ 章节阅读页**：`chapter-reader.js` 按 `chapterId + status:'published'` 查章节并渲染正文。**这一步先不加付费判断**，只验证路由、数据按 ID 取到、正文渲染。

**⑨ 第一次自测**：首页出卡片 -> 详情页出章节列表 -> 阅读页出正文，6 步全通即完成最小可运行项目。

**⑩ 排错速查**：首页空白查 `wx.cloud.init` 环境 ID / books 集合数据 / isPublished / 控制台报错；详情无章节查 bookId 一致性 / status / chapterOrder；阅读无正文查路由参数与 chapterId；跳转报错查 `app.json` 声明；**数据超过 20 条只显示 20 条是云数据库默认限制**（`get()` 单次最多 20 条，需 skip/limit 分页或云函数中转最多 100 条）。

**⑪ 安全提示**：当前教程直接客户端读云数据库，适合学习与原型。正式上线前必须：为每个集合配置安全规则（books/chapters 仅允许读、orders 仅允许写）；**付费章节正文不应直接暴露在客户端查询中，应改用云函数控制返回内容。**

**⑫ 下一步**：① 加微信登录（识别谁在看）→ ② 给章节加权限层（isVIP 赋值 + 阅读页权限判断 + 付费墙）→ ③ 接入支付（先 VIP 后单章，状态机更简单）。

### 4.11 成本与代价

初期成本：小程序认证/资质、云开发资源消耗、微信支付相关成本、可能的后台托管、域名（可选）。**它真正的代价不是服务器钱，而是平台规则、审核门槛、产品自由度受限、SEO 能力弱——把代价从工程复杂度转移到了平台约束。**

## 第五部分：方案 D — PocketBase + Nuxt 3（低成本 MVP）

### 5.1 为什么它适合小项目起步

PocketBase 几乎可以理解为：**一个单二进制程序，自带 SQLite 数据库、后台、用户认证、文件上传、API、权限规则**。部署甚至可以是"1 台低配 VPS + PocketBase + 前端站点"。

**优势：** 实现简单度极高、成本极低、后台开箱即用、适合章节/书籍/用户/订单/评论/阅读进度这些标准数据模型、小规模性能足够。

**缺点：** SQLite 在超高并发/多写入/复杂高事务下不如 PostgreSQL；生态与社区规模不如 Next.js/Supabase/Payload；大型工作流/复杂访问控制/内容建模能力不如 Payload 专业；未来几十万用户可能要迁移。

### 5.2 推荐架构

```text
前端：Nuxt 3（SSR/SEO 友好，内容站体验好）
后端：PocketBase
支付：独立 webhook 服务或 Nuxt server routes
存储：PocketBase 文件 / R2 / S3
搜索：初期不用；后期再接 Meilisearch

PocketBase 数据模型：users、books、chapters、purchases、comments、reading_progress（admin UI 内建）
```

**为什么推荐 Nuxt 3 而不是 Next.js：** 在"内容站 + SSR + SEO + 上手平滑"场景，Nuxt 3 的路由与数据获取心智负担更低、中小项目结构更清晰、服务端 API 与页面协同更自然。

### 5.3 结论

**如果你想要"比 Next.js + Supabase 更简单、更便宜，还能保留独立站能力"，PocketBase + Nuxt 3 是非常强的候选；个人开发者早期 MVP 尤其合适，验证成功后可迁移到 Payload / Postgres。**

## 第六部分：方案对比与选择指引

| 需求维度 | 选它 |
|----------|------|
| 长期品牌站 + 强后台 + 少造轮子 | **Payload CMS 3** |
| 低成本独立站 MVP + 技术简单 | **PocketBase + Nuxt 3** |
| 熟悉 React/TS + 要长期工程自由度 | **Next.js + Supabase**（删减复杂度） |
| 中文移动端 + 支付转化优先 | **微信小程序 + 云开发** |
| 纯商业验证、零开发 | **SaaS / 微信生态** |

所有方案的共享铁律（无论选哪个）：
1. VIP 是订阅状态，不是角色。
2. 章节权限判断顺序固定（免费 → 登录 → 单章 → 整本 → VIP）。
3. 支付只认服务端回调，回调必须幂等（CAS pending → completed）。
4. 余额/订单/VIP 客户端只读，写操作走服务端。
5. 付费正文只在服务端读取后渲染。
