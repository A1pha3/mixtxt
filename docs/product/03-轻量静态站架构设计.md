## 第一部分：共享基础设计（三套静态方案通用）

以下规则在 Hugo / Astro + Keystatic / Astro + Pages CMS 中全部成立，各方案只是实现方式不同。**先读这部分，再去看具体方案。**

### 1.1 方案成立的边界

"管理创作"明确理解为：作者能方便地维护 Markdown 文件、提交版本、预览站点、发布内容，**而不是在网站前台提供一个在线后台**。

| 场景 | 静态方案是否合适 | 判断 |
|------|------------------|------|
| 单作者写作，本地或 GitHub 网页端编辑 Markdown | ✅ | 正好匹配 |
| 读者只读，不登录、不评论、不购买 | ✅ | 静态站天然适合 |
| 作者通过 Git 查看、回滚、标记版本 | ✅ | Git 是正本版本系统 |
| 读者在网页上切换大版本 | ⚠️ | 可以做，但需要按 tag / 分支额外构建 |
| 读者在网页上查看每章所有历史 diff | ⚠️ | 需要脚本生成静态 diff 页面 |
| 网站内置在线编辑后台 | ⚠️/✅ | Hugo 不提供；Astro + CMS 可提供网页编辑 |
| 付费章节 / VIP / 订单 / 登录 | ❌ | 必须切换到动态方案（见文档 02） |

### 1.2 内容模型（五类内容）

无论哪套静态方案，内容正本都围绕这五类（细节字段因方案略有差异）：

| 类型 | 格式 | 用途 |
|------|------|------|
| site 配置 | JSON | 网站标题、描述、作者、社交链接 |
| books | JSON | 书籍元数据（slug、title、status、summary、cover、tags、版权状态） |
| chapters | Markdown + YAML frontmatter | 章节正文（book、order、title、status、summary、ai 记录、seo） |
| releases | Markdown + YAML frontmatter | 发布版本说明（book、version、date、gitTag） |
| prompts | Markdown + YAML frontmatter | AI 改编提示词模板（作者侧资产） |

**书籍字段核心：** title、slug（小写英文数字短横线）、original（原作）、status（planning/serializing/completed/paused）、visibility（public/hidden）、summary、cover、tags、copyrightStatus（public-domain/authorized/private-draft/unknown）、startedAt、updatedAt、seo。

**章节字段核心：** book、chapterNo（三位数字如 001）或 order、title、slug、status（draft/review/published/archived）、summary、wordCount、createdAt、updatedAt、ai（model/prompt/humanEdited）、seo。

**硬约束：** `copyrightStatus` 为 `private-draft` 时 `visibility` 必须为 `hidden`；`copyrightStatus` 为 `unknown` 时不能公开。构建校验脚本强制检查，违反时构建失败。

### 1.3 章节组织与导航（不跨书）

**章节文件组织两种方式：**

- **按书嵌套目录**（Hugo 风格）：`content/<book>/001-楔子.md`，书 = 一个 section。
- **平铺 + 文件名前缀**（Pages CMS 推荐）：`src/content/chapters/{book}-{chapterNo}-{slug}.md`，如 `sanguo-scifi-002-huangjin.md`。好处：Pages CMS 文件名模板更简单、Astro 只需按 `book` 字段过滤、Git 里一眼看出归属；章节多时可再迁移到子目录。

**章节导航铁律：不要跨书。** 每章只取同一本书内的已发布章节，按 order/chapterNo 排序，再算上一篇/下一篇：

```ts
const chapters = (await getCollection("chapters"))
  .filter((chapter) => chapter.data.book === book && !chapter.data.draft)
  .sort((a, b) => a.data.order - b.data.order);
const currentIndex = chapters.findIndex((chapter) => chapter.data.slug === slug);
const prevChapter = chapters[currentIndex - 1] ?? null;
const nextChapter = chapters[currentIndex + 1] ?? null;
```

Hugo 模板中对应写法（限制在当前 section 内，`ByWeight.Reverse` 让 Prev/Next 符合中文"上一章/下一章"直觉）：

```go-html-template
{{ $pages := .CurrentSection.Pages.ByWeight.Reverse }}
{{ with $pages.Prev . }}<a href="{{ .RelPermalink }}">上一章</a>{{ end }}
{{ with $pages.Next . }}<a href="{{ .RelPermalink }}">下一章</a>{{ end }}
```

### 1.4 版本管理（三层模型）

版本管理不是一个单点功能，拆成三层：

| 层级 | 面向谁 | 实现方式 | 首版是否做 |
|------|--------|----------|------------|
| 内部版本 | 作者 | 每章提交 `git commit`，用 `git log` / `git diff` / `git checkout` 查看和回滚 | ✅ 必做 |
| 发布大版本 | 作者和读者 | 用 Git tag 标记 `v0.1.0`、`v1.0.0`，在书页写版本说明（releases） | ✅ 建议做 |
| 网页历史版本 | 读者 | 按 tag / 分支构建多个静态站点，部署到 `/versions/v1.0.0/` 或子域名 | ⚠️ 第二阶段 |
| 逐章历史 diff | 读者 | 写脚本读取 Git 历史，生成静态 diff 页面 | ⚠️ 需求明确后 |

**首版不要追求"每一章所有历史版本都能在网页上切换"**——那会把静态站点变成一个 Git 历史可视化系统。给读者看的版本变化用 releases 版本说明页，不直接看 Git log。

```bash
# 写完一章
git add content/三国演义-科幻版/002-黄巾初起.md
git commit -m "feat: 黄巾初起"
# 大改节点打 tag
git tag v0.2.0 && git push origin v0.2.0
```

### 1.5 部署与平台限制（Cloudflare Pages）

**Cloudflare Pages 免费层限制（2026-06 时点）：**

- 每月 500 次构建
- 同一时间 1 个构建任务
- 单站点最多 20,000 个文件
- 单个静态资源最大 25 MiB

**构建频率策略（重要）：** 构建次数按账号维度管理，不要假定每个 Pages 项目都有独立 500 次额度。建议本地预览确认后再集中 push，每天 1-3 次，每月新增构建控制在 30-90 次。

**文件数量估算：** 100 本书 × 100 章 = 10,000 个章节页，加索引/标签/搜索资源仍大概率低于 20,000 上限。若按每个 Git tag 部署历史版本，文件数按版本倍增，需重新评估。

### 1.6 版权边界（与技术栈无关，但决定能否公开运营）

"AI 改编著名小说"不等于自动可公开发布：

- 首批只处理**公版作品**（如《三国演义》），或已获授权的内容。
- 非公版改编稿只作为私人草稿保存（visibility=hidden）。
- 只要站点对外公开，就要确认原作是否进入公版、改编是否有授权、是否涉及商用传播。
- 技术实现上：`copyrightStatus === "unknown"` 的书籍不允许公开构建（构建失败）。

### 1.7 草稿过滤铁律

- 草稿（draft/review）章节**不进入**公开页面、RSS、sitemap、Pagefind 搜索索引。
- 不要在页面里渲染草稿后再用 CSS 隐藏——静态站一旦构建进 `dist` 就可能被访问。
- 公开页面统一通过工具函数获取内容（如 `getPublishedChapters()`），过滤规则保持一致。

### 1.8 搜索方案（Pagefind）

Pagefind 不需要搜索服务端：构建完站点后扫描 `dist` 目录生成静态索引。

```bash
astro build
npx pagefind --site dist
```

- 章节正文 `<article>` 上加 `data-pagefind-body` 进入索引。
- **一旦站内使用了 `data-pagefind-body`，Pagefind 只索引显式标记的元素**——导航、页脚、首页、版本页不添加即不索引。
- 私有内容不能进入公开构建产物，静态搜索没有权限校验。

### 1.9 静态方案的共同边界

- **不能在线编辑**：Hugo 只能本地/GitHub 网页端改 Markdown；Astro + CMS 有网页编辑 UI，但仍是文件正本。
- **章节数过大时构建时间**：千章内秒级；数千至数万章仍是秒级到十几秒；超过数万章按书拆多项目或用 `--gc`。
- **SEO 与全文公开**：长篇小说全文铺在 HTML 里可能被搜索引擎抓取展示；不想被索引用 robots.txt / noindex / 只公开摘要页，不要改成 JS 加载正文（SEO 变差）。
- **没有评论/点赞/阅读统计**：如需后插 Giscus/Artalk（评论）、Umami/Plausible（统计），不影响主结构。
- **主题升级**：Hugo 主题用 Git submodule 固定到 commit/tag，升级前看 changelog 并本地预览。

## 第二部分：推荐方案 — Astro + Pages CMS（完整设计）

### 2.1 结论与设计边界

**目标不是做一个复杂的小说平台，而是做一个足够优秀、足够轻、长期不容易后悔的单作者 AI 改编小说创作网站。**

```text
Astro + Pages CMS + Pagefind + GitHub + Cloudflare Pages
```

保留的条件：正文仍是 Markdown 文件、不需要数据库、只有你一个创建者读者只读、Git 保存版本、Cloudflare Pages 自动构建发布。比纯 Hugo 更好的地方：Astro 更适合做定制阅读器和内容应用；Pages CMS 给 GitHub 仓库内容补网页编辑界面；Pagefind 让站内搜索不用后端也能做。

**本方案暂时不做：** 用户注册/登录、付费章节/VIP、评论/点赞/收藏、在线 AI 生成并保存、多作者协作后台、读者查看逐字历史 diff。

### 2.2 系统总览

```mermaid
flowchart LR
    A["AI 生成草稿"] --> B["作者修订"]
    B --> C["Pages CMS 或本地编辑器"]
    C --> D["Markdown / JSON 文件"]
    D --> E["GitHub 仓库"]
    E --> F["Cloudflare Pages 构建"]
    F --> G["Astro 生成 HTML"]
    G --> H["Pagefind 生成搜索索引"]
    H --> I["Cloudflare CDN"]
    I --> J["读者阅读网站"]
```

**一次章节发布如何流动：** AI 生成草稿 → Pages CMS 新建章节（book/章节号/标题/slug/摘要/状态/正文）→ 保存为 `src/content/chapters/{book}-{chapterNo}-{slug}.md` → 写回 GitHub 产生 commit → Cloudflare Pages 触发 build → Astro 读取 chapters 过滤 `status === "published"` → 生成书页/章节页/标签页/RSS/sitemap → Pagefind 只索引已构建公开页面 → CDN 发布。

### 2.6 Content Collections schema（硬约束）

```ts
import { defineCollection } from "astro:content";
import { z } from "astro/zod";
import { glob } from "astro/loaders";

const slugPattern = /^[a-z0-9]+(?:-[a-z0-9]+)*$/;
const chapterNoPattern = /^[0-9]{3}$/;
const seoSchema = z.object({ title: z.string().optional(), description: z.string().optional() }).optional();

const books = defineCollection({
  loader: glob({ pattern: "*.json", base: "./src/content/books" }),
  schema: z.object({
    title: z.string(),
    slug: z.string().regex(slugPattern),
    original: z.string().optional(),
    author: z.string().optional(),
    adaptor: z.string().optional(),
    status: z.enum(["planning", "serializing", "completed", "paused"]),
    visibility: z.enum(["public", "hidden"]).default("public"),
    summary: z.string(),
    cover: z.string().optional(),
    tags: z.array(z.string()).default([]),
    copyrightStatus: z.enum(["public-domain", "authorized", "private-draft", "unknown"]),
    startedAt: z.string(),
    updatedAt: z.string(),
    seo: seoSchema,
  }),
});

const chapters = defineCollection({
  loader: glob({ pattern: "*.md", base: "./src/content/chapters" }),
  schema: z.object({
    book: z.string().regex(slugPattern),
    chapterNo: z.string().regex(chapterNoPattern),
    title: z.string(),
    slug: z.string().regex(slugPattern),
    status: z.enum(["draft", "review", "published", "archived"]),
    summary: z.string(),
    wordCount: z.number().int().nonnegative().optional(),
    createdAt: z.string(),
    updatedAt: z.string(),
    ai: z.object({
      model: z.string().optional(),
      prompt: z.string().optional(),
      humanEdited: z.boolean().default(true),
    }).optional(),
    seo: seoSchema,
  }),
});

const releases = defineCollection({
  loader: glob({ pattern: "*.md", base: "./src/content/releases" }),
  schema: z.object({
    book: z.string().regex(slugPattern),
    version: z.string(),
    versionSlug: z.string().regex(slugPattern),
    title: z.string(),
    date: z.string(),
    gitTag: z.string().optional(),
  }),
});

const prompts = defineCollection({
  loader: glob({ pattern: "*.md", base: "./src/content/prompts" }),
  schema: z.object({
    title: z.string(),
    slug: z.string().regex(slugPattern),
    category: z.enum(["rewrite", "style", "outline", "character", "review"]),
    status: z.enum(["active", "archived"]),
    updatedAt: z.string(),
  }),
});

export const collections = { books, chapters, releases, prompts };
```

**schema 是实现时的硬约束**：AI 实现项目时不应随意改字段名；如果要改，必须同时更新 Pages CMS 配置、页面查询逻辑和示例内容。

### 2.8 Pages CMS 配置（.pages.yml）

Pages CMS 通过仓库根目录 `.pages.yml` 读取配置，只负责编辑文件。要点（完整字段定义见原设计文档）：

- **media**：covers（public/covers → /covers，jpg/jpeg/png/webp）、chapter_images（public/images/chapters → /images/chapters）。
- **site**：`type: file`，编辑 src/data/site.json（title/description/author/defaultLanguage/baseUrl/github/copyright）。
- **books**：`type: collection`，format json，filename `{slug}.json`；字段含 title、slug（pattern 校验）、status、visibility、summary、cover（image）、tags、copyrightStatus、startedAt、updatedAt（readonly）、seo。
- **chapters**：`type: collection`，format yaml-frontmatter，filename `{book}-{chapterNo}-{slug}.md`；book 用 reference 关联 books；chapterNo 三位数字；status 默认新建选 draft；wordCount 与 updatedAt readonly（构建脚本自动更新）；body 用 rich-text（format: markdown）。
- **releases**：book（reference）、version、versionSlug、title、date、gitTag、body。
- **prompts**：title、slug、category、status、updatedAt、body。

**Pages CMS 使用约束：** 字段名必须与 Astro schema 一致；`chapters.body` 是特殊字段写到 frontmatter 下面的 Markdown 正文；封面写入 /covers，插图写入 /images/chapters；不要让 CMS 管理 src/pages、src/components 等代码文件；Pages CMS 不支持 `type: group`，四个 collection 直接放 content 顶层。

### 2.9 页面设计

| 页面 | 核心内容 | 验收 |
|------|----------|------|
| 首页 `/` | 最近更新（8-10 个 published 章节）、书籍列表（public）、标签入口、版权提示 | 草稿/隐藏书籍不显示；移动端第一屏能看到书或更新 |
| 书籍列表 `/books/` | 筛选（状态/标签）、排序、卡片 | 纯前端 JS 筛选即可 |
| 书籍详情 `/books/[book]/` | 封面/元信息/简介/标签/版权状态、章节目录（只显示 published，按 chapterNo 升序）、最近版本说明、开始阅读按钮 | 章节按 chapterNo 排序，草稿不显示 |
| 章节页 `/books/[book]/[chapter]/` | 标题/摘要/正文、上一章/下一章（不跨书）、目录抽屉、阅读工具栏、返回书页 | 无上一章时按钮 disabled |
| 搜索 `/search/` | Pagefind 静态索引 | 能搜到 published，搜不到草稿 |
| 标签 `/tags/[tag]/` | 标签下书籍 | 首版只对书籍打标签 |
| 版本 `/releases/` | 版本说明按日期倒序，可按书过滤 | 链接到 Git tag 无 tag 不报错 |
| 关于 `/about/` | 项目说明、AI 创作说明、版权边界、联系方式 | — |

**章节页 title 格式：** `{chapterNo} {chapterTitle} - {bookTitle} - {siteTitle}`；书籍页：`{bookTitle} - {siteTitle}`。

**路由实现：** 书籍页/章节页用 `getStaticPaths()` 生成（书籍页遍历 getPublicBooks；章节页双层遍历 getPublicBooks × getPublishedChapters）。

### 2.10 阅读体验与样式

- 页面背景接近纸张的浅灰（不要纯白刺眼）；正文字号默认 18px；行高默认 1.8；阅读区最大宽度 720px；段落间距稳定。
- CSS token 用变量（--color-bg/surface/text/muted/border/accent、--reader-width/font-size/line-height），`[data-theme="dark"]` 覆盖暗色变量。
- 阅读工具栏：字号（小/中/大）、行距（紧凑/标准/宽松）、主题（浅色/暗色/跟随系统）、页面宽度（标准/宽），存 localStorage。
- 进度记忆 key：`mixtxt.reader.lastChapter.{bookSlug}`，首页/书籍页显示"继续阅读"入口。
- 移动端：顶部导航不遮挡正文、章节页底部必须有上一章/下一章、阅读设置面板可收起、正文宽度 `min(100%, var(--reader-width))`。
- 不做单色系大面积渐变，小说站要稳、耐看。

### 2.11 SEO / RSS / sitemap

- 每页必须有 title、description、canonical、Open Graph。
- RSS 只含最近发布章节（标题 `{bookTitle}: {chapterNo} {chapterTitle}`，日期 updatedAt，描述 summary），可用 `@astrojs/rss` 或手写 XML，**必须只含 published**。
- sitemap 含：首页、书籍列表、公开书籍页、published 章节页、标签页、版本页；**不含** draft/review 章节、hidden 书籍、未公开的 prompts。
- robots.txt 允许索引公开页面；如果不希望全文被索引，就不要公开章节全文（静态 HTML 无法可靠阻止复制）。

### 2.12 部署（Cloudflare Pages）

```text
Framework preset: Astro
Build command: npm run build
Build output directory: dist
Root directory: /
Environment variables: NODE_VERSION 使用当前 Node.js LTS
```

`public/_headers` 缓存策略：HTML `max-age=3600`（别设过长，避免发布后读者看到旧内容）；`/_astro/*`、`/covers/*`、`/images/*`、`/pagefind/*` 设 `max-age=31536000, immutable`；加 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy`。

### 2.13 AI 创作工作流

首版不把 AI 接口接到站内。流程：选择原作和改编方向 → 用 prompts 模板生成章节草稿 → 人工修订事实/节奏/人物动机 → Pages CMS 新建章节 status=draft → 本地预览或 Cloudflare preview 检查 → 改 published → push 触发构建。

每章 frontmatter 的 `ai` 字段记录使用的 prompt slug、模型、是否人工修订；**不要把完整模型输出历史塞进 frontmatter**（需保留另存私有笔记或 git ignored 文件）。

### 2.14 测试与验收（validate-content.mjs）

构建前必须跑内容校验脚本，规则包括：

- site.json 必须含 title/description/author/defaultLanguage/baseUrl，baseUrl 是完整 URL。
- 无重复 book slug；文件名必须 `{slug}.json`。
- 同一本书内无重复 chapter slug / chapterNo；文件名必须 `{book}-{chapterNo}-{slug}.md`。
- published 章节所属 book 必须存在，且该 book 是 public 且 copyrightStatus 可公开。
- public book 的 copyrightStatus 不能是 unknown/private-draft；private-draft 时 visibility 必须 hidden。
- releases 的 version 是 semver；releases book 存在。
- 无重复 prompt slug；chapters 的 ai.prompt 引用必须存在。
- 日期格式 YYYY-MM-DD；chapters createdAt 不晚于 updatedAt。
- cover 文件存在。

### 2.15 实施计划

- **Phase 0 初始化**：创建 Astro 项目、装 Pagefind、基本 CSS、示例内容。验收：dev/build 通过。
- **Phase 1 内容模型和路由**：content.config.ts、site.json + 四类示例、lib/content.ts、首页/书籍页/章节页。验收：公开内容显示正确、草稿不显示、上/下一章正确。
- **Phase 2 Pages CMS**：.pages.yml、连接 GitHub、测试新增书籍/章节/上传封面。验收：CMS 保存后 build 仍通过、文件名符合约定、字段与 schema 对齐。
- **Phase 3 阅读器体验**：ReaderLayout、ReaderToolbar、目录抽屉、暗色/字号/行距/宽度、移动端适配。
- **Phase 4 搜索和 SEO**：Pagefind、search 页、RSS、sitemap、meta/OG。
- **Phase 5 部署**：GitHub 连 Cloudflare Pages、配置 build、自定义域名、检查 build 次数与缓存 headers。

### 2.16 AI 实施守则

1. 不要引入数据库、用户登录。
2. 不要把草稿渲染到公开页面。
3. 不要改动核心字段名。
4. 所有内容查询集中到 `src/lib/content.ts`，页面都通过工具函数获取。
5. 章节导航必须按同一本书内的 chapterNo 计算。
6. 搜索索引只能来自构建后的公开页面。
7. Pages CMS 配置和 Astro schema 必须同步。
8. 实现完成后必须跑 `npm run build`。

优先顺序：内容模型 → 内容查询 → 页面路由 → 阅读器 → CMS 配置 → 搜索 → 部署。**不要先做复杂视觉效果。**

### 2.17 风险与应对

| 风险 | 应对 |
|------|------|
| CMS 字段和 schema 不一致导致构建失败 | 字段名统一，build 前跑内容校验 |
| Cloudflare build 次数不够 | 本地预览后集中 push，减少 preview build |
| 草稿进入公开页面 | 统一用 getPublishedChapters() |
| Pagefind 索引草稿 | 草稿不参与静态构建 |
| 文件数超过限制 | 控制历史版本页数量，必要时拆站或升级 |
| 原作版权不清 | unknown 不允许公开构建 |
| 依赖升级破坏构建 | 固定 lockfile，升级前本地构建 |
| 构建失败读者看到旧版本 | 构建失败时旧版本仍在线；建议 GitHub Actions 本地构建门控，push 前自动跑 build |

## 第三部分：备选方案 1 — Hugo + Git（最快上线）

### 3.1 结论

在"单作者、Markdown 正本、无数据库、读者只读"前提下，**Hugo 适合本需求**。整条链路非常轻：作者本地或 GitHub 网页端写 Markdown，Git 保存版本，Hugo 生成静态页面，Cloudflare Pages / Vercel / GitHub Pages 发布。

**为什么 Hugo 在这里是首选：** ① 编译速度对"AI 写小说"特别友好（AI 批量生成章节常态，Hugo 数千页秒级构建，`hugo server` 改一行即时刷新）；② 目录结构天然映射"一本书 = 一个 section"；③ Git 既是版本管理、又是部署入口（push 即发布）；④ 无数据库、无服务端，读者只读天然安全。

**它不能满足的：** 网页后台在线编辑（需要接 Decap CMS / TinaCMS 或换动态方案）、读者网页版本切换（需按 tag 额外构建）、逐章 diff 页面。

### 3.2 技术栈

```text
内容源:     content/<book-slug>/*.md
模板:       Hugo 主题（Blowfish / Book / PaperMod / hugo-book）
数据:       无（Markdown front matter 即数据）
写作管理:   VSCode / Obsidian / GitHub 网页端
版本:       Git
构建:       Hugo（extended 版本）
托管:       Cloudflare Pages（推荐）/ GitHub Pages / Vercel / Netlify
域名:       可选，约 ¥60/年
CI:         托管平台内建，无需自配
```

### 3.3 最小可用项目结构

```text
mixtxt/
├── config.toml             # Hugo 配置
├── content/
│   ├── _index.md           # 首页：所有书籍列表
│   └── 三国演义-科幻版/
│       ├── _index.md       # 书页：简介 + 章节列表
│       ├── 001-楔子.md
│       ├── 002-黄巾初起.md
│       └── ...
├── themes/<主题名>/
├── static/                 # 封面图、字体等
├── .github/workflows/      # 可选：自定义 CI
└── README.md
```

每篇 Markdown front matter：

```markdown
---
title: "002 黄巾初起"
weight: 2
date: 2026-06-02T10:00:00+08:00
draft: false
summary: "巨鹿张角起事，天下震动。"
---
```

### 3.4 章节关联与版本管理

- **同 section + weight 排序**：一本书所有章放同一目录，Hugo 按 weight 排序；上一篇/下一篇模板限制在当前 section（见 1.3 节模板）。
- **跨书引用**：`{{< ref "path/to/chapter" >}}` 短代码或相对链接。
- 版本管理见 1.4 节；给读者版本切换：每个发布版本打 git tag → 托管平台为每个 tag 部署一份（子域名/子路径）→ 站点底部加"切换版本"下拉，不需要写服务端代码。

### 3.5 起步命令与成本

```bash
brew install hugo            # macOS
hugo new site mixtxt && cd mixtxt && git init
git submodule add https://github.com/nunocoracao/blowfish.git themes/blowfish
git -C themes/blowfish checkout <稳定版本>   # 固定版本，避免漂移
hugo server -D               # 本地预览
hugo --minify                # 构建
```

**成本：** Hugo/主题 ¥0、Cloudflare Pages 托管+CDN+HTTPS ¥0、Git 仓库 ¥0、可选域名 ¥60-80/年。**合计月度约 ¥0（不含域名）。** 从 0 到上线 1-2 周（学会 Hugo+Git 1-2 天、配置 CI/主题 1-3 天、写第一本书 2-5 天）。

### 3.6 与 Astro + Pages CMS 的取舍

| 对比项 | Hugo | Astro + Pages CMS |
|--------|------|-------------------|
| 构建速度 | 更快 | 较快，通常慢于 Hugo |
| 依赖复杂度 | 更低 | 更高，需 Node 生态 |
| Markdown 正本 | 支持 | 支持 |
| 内容 schema 校验 | 弱，需自写校验 | 强，Content Collections 原生适合 |
| 网页编辑 UI | 需接额外 CMS | Pages CMS 集成更自然 |
| 阅读器交互 | 可做，模板体系不如 Astro 顺 | 更自然 |
| 首版上线速度 | Hugo 更快 | Astro 稍慢 |

**判断：** 第一目标是"最少折腾、最快上线"选 Hugo；第一目标是"内容结构稳、作者编辑体验好、阅读器可扩展"选 Astro + Pages CMS。**如果还没开始实现，Astro + Pages CMS 值得作为首选试一次；如果已经用 Hugo 跑通了，没必要为了技术洁癖迁移。**

## 第四部分：备选方案 2 — Astro + Keystatic（组件化 + 编辑 UI）

### 4.1 与推荐方案的差异

Astro + Keystatic 与 Astro + Pages CMS 定位几乎相同（Markdown 正本 + 无数据库 + 静态发布 + 网页编辑入口），差异在于编辑 UI 由 **Keystatic** 提供，更适合"想要更细的内容结构校验 + 更自然的阅读器组件化"。

- **章节元数据更不容易乱**：Content Collections 给 front matter 加 schema，构建时发现字段缺失/类型错误。
- **阅读体验更容易组件化**：字号切换、暗色、目录抽屉、进度、封面卡片用 Astro 组件比 Hugo 模板自然。
- **网页编辑入口**：Keystatic 提供管理 UI，保存后仍落到 Git 仓库，内容正本还是文件。
- **后续扩展平滑**：未来接 Cloudflare Pages Functions / D1 / KV / R2 时，Astro 结构更容易承接。

代价：Node 工具链更重、依赖更多、构建通常慢于 Hugo、首次配置 Keystatic 和 schema 要多花时间。

### 4.2 内容模型与 schema

目录结构与推荐方案类似，区别：books 用 JSON、chapters 按书嵌套目录（`src/content/chapters/{book}/001-prologue.md`）、releases 用 JSON 数组。chapters frontmatter 核心字段：book、title、slug、order（正整数）、draft、summary、createdAt、updatedAt。schema 用 `z.object` 校验（books/chapters/releases 三个 collection；落地时可以先不做 releases）。

**章节导航算法**与 1.3 节相同：filter book + !draft → sort order → findIndex → prev/next。

### 4.3 Keystatic 配置要点

- **两种模式：** Local mode（本地写作/调试，保存到本地文件系统，首版先用）→ GitHub mode（网页编辑并写回仓库）。
- `keystatic.config.ts` 定义 books / chapters collection，字段与 Astro schema **对齐**（slug 用 fields.slug 时检查实际写出的文件名和 frontmatter 是否与 Astro schema 一致；不一致就把 slug 改成普通 text 字段）。
- **后台访问控制：** Keystatic 不是公开后台——只给作者自己的 GitHub 账号写权限；管理入口不放主导航；部署公网管理界面额外用 Cloudflare Access 保护 `/keystatic`；不要当多作者协作系统。

### 4.4 搜索与部署

- Pagefind：`astro build` 后 `npx pagefind --site dist`，package.json scripts 串联。
- Cloudflare Pages：Build command `npm run build`（或 pnpm build），output `dist`；免费层限制与构建频率策略同 1.5 节。
- 风险同推荐方案：Keystatic 不是完整 CMS（不是订单后台/权限系统/审核系统）；静态站没有读者权限（草稿必须在构建阶段过滤）；搜索索引会暴露正文（私有内容不能进构建产物）；改编作品版权风险。

### 4.5 实施计划

Phase 1 验证内容结构（初始化、两个 collection、1 书 3 章、首页/书页/章节页、排序与导航）→ Phase 2 接入 Keystatic（安装、配置、本地 /keystatic 编辑、确认文件符合 schema、再决定切 GitHub mode）→ Phase 3 阅读体验 + 搜索 → Phase 4 部署和版本管理。

## 第五部分：三方案对比与选择指引

| 需求 | 选择 |
|------|------|
| 最快上线、最少折腾、纯 Git 工作流 | **Hugo + Git** |
| 网页编辑后台 + 内容结构校验 + 定制阅读器（综合首选） | **Astro + Pages CMS** |
| 组件化内容应用 + 编辑 UI、想要更强的 schema 校验 | **Astro + Keystatic** |
| 出现付费/用户/VIP 需求 | 切换到动态方案（文档 02） |

**三方案共享铁律：**
1. 内容正本是 Git 仓库里的 Markdown/JSON 文件，无数据库。
2. 草稿不进构建、不进搜索、不进 sitemap。
3. 章节导航不跨书，按 order/chapterNo 排序。
4. 版本管理三层：Git commit（内部）→ Git tag + releases（发布版本）→ 按 tag 构建（读者历史版本，后置）。
5. 版权边界：公版或授权才可公开；unknown 不允许公开构建。
6. Cloudflare Pages 免费层：500 构建/月、20,000 文件、25 MiB，按账号维度管理构建量。
